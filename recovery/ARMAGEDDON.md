# Армагеддон — карточка

**Цель:** поднять Ядро на новой машине за ≤ 60 минут, не имея доступа к старым файлам.
**Два читателя:** человек → `ARMAGEDDON-HUMAN.md`, агент → `ARMAGEDDON-LLM.md`.

## Что должно быть вне сервера

| Что | Зачем | Где хранится |
|---|---|---|
| Пароль шифрования снимков | без него снимок — мусор | менеджер паролей |
| Ключ провайдера модели | без него Пиксель не думает | менеджер паролей |
| Ключ S3 | достать снимок | менеджер паролей |
| Доступ к домену / NS | переключить трафик | регистратор |
| Эта карточка и регламент | порядок действий | распечатка / менеджер |

## Порядок (не переставлять)

1. **Машина.** Debian 13, 4 vCPU / 8 ГБ / 60 ГБ, root по ключу.
2. **Пиксель.** `git clone` + `./install.sh`.
3. **Ключ модели.** `~/.pixel/provider.key`, права 600.
4. **Осмотр.** `pixel doctor` — красное доустановить.
5. **Связь.** `pixel "ответь одним словом"` — если не отвечает, дальше нет смысла.
6. **Снимок.** Самый свежий целый, манифест сходится. Битый — предыдущий.
7. **База.** Роль, БД, восстановление дампа, сверка счётчиков.
8. **Код и процессы.** Клон репозитория, `npm ci`, pm2, `pm2 save`.
9. **Сайт.** nginx-конфиги, `nginx -t`, certbot.
10. **Приёмка.** `/health` зелёный, панель отвечает, бот отвечает, один клиентский сайт открывается.

## Стоп-условия

- Манифест снимка не сходится → не восстанавливать, взять предыдущий.
- Процесс падает в цикле → читать логи, не перезапускать вслепую.
- Модель не отвечает → не начинать подъём.
- Любое необратимое (удаление, смена секретов, DNS) → спросить человека.

## Известные грабли (из прошлых учений)

- `node term.js` — модуль, а не демон: запускать надо `bin/pixel.mjs`.
- Публичный бакет = утечка. Снимки только в приватный.
- Планировщик копий со сдвигом якоря теряет сутки (RPO наблюдался 28 ч).
- Проверка «файл есть» ничего не доказывает: проверяй `/health` и открытие страницы.

## Сценарий F. Домен потерян

**Что происходит:** сервер жив или мёртв, но `fridaybot.ru` недоступен — регистратор
заблокировал, дата-центр потерял зону, оплата не прошла, домен отозван. Перепривязать
IP некуда: домена нет.

**Почему это отдельный сценарий:** все предыдущие шаги заканчиваются словами
«открыть https://fridaybot.ru/core/health». Если домена нет — проверять нечего,
и восстановление формально «успешно», а продукта нет.

### Что должно быть готово заранее

| Что | Зачем | Требование |
|---|---|---|
| **Запасной домен** | работать, пока основной недоступен | куплен **заранее** на 2+ года, у **другого** регистратора |
| **DNS у третьей стороны** | перепривязать IP, если регистратор недоступен | Cloudflare / Яндекс DNS / deSEC, NS прописаны у регистратора |
| **Доступ к регистратору** | продлить/разблокировать | логин, 2FA-коды — в менеджере паролей вне сервера |
| **Список зависимостей домена** | переключить за один проход | чек-лист ниже |

Сейчас: домен `fridaybot.ru` у **Beget**, DNS там же (`ns1.beget.com`). Регистратор,
DNS и часть услуг — один поставщик. Это одна точка отказа на три роли.

### Чек-лист переезда на новый домен

1. DNS нового домена → IP нового сервера (A-запись, TTL заранее снизить до 300).
2. `restore.sh` с `DOMAIN=новый.домен`: подменяет `server_name` в nginx-конфигах.
3. Сертификат: `certbot --nginx -d новый.домен -d www.новый.домен`.
4. Яндекс OAuth: redirect URI → `https://новый.домен/core/oauth/callback` (иначе вход не работает).
5. Telegram: `setWebhook` на новый домен; проверить кнопки и ссылки в боте.
6. S3: CORS и публичные ссылки, если они содержат старый домен.
7. Письма и подписи: ссылки в шаблонах.
8. Клиентские сайты: у них свои домены, но проверять по одному.
9. Панель: абсолютные ссылки в ответах агента.

### Чего не делать

- Не менять DNS основного домена «на всякий случай», пока запасной не проверен.
- Не покупать запасной домен у того же регистратора: смысл в независимости.
- Не хранить доступ к регистратору только на сервере — он и есть то, что теряется.
