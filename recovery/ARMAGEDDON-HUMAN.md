# Армагеддон — инструкция для человека

Читать, когда сервера нет. Без терминального жаргона. Всё, что нужно: новый сервер,
доступ к домену и три вещи, которые хранятся **вне** старого сервера.

---

## Что должно быть вне сервера (проверь сегодня, а не в день аварии)

1. **Пароль шифрования снимков** — в менеджере паролей.
2. **Ключ провайдера модели** (DeepSeek) — там же.
3. **Доступ к домену** (логин регистратора, NS).
4. **Адрес бакета со снимками** и ключ к нему.
5. Эта инструкция и `ARMAGEDDON-LLM.md` — распечатаны или в менеджере.

Нет любого пункта — восстановление встанет именно на нём.

---

## Шаг 0. Домен — проверить до всего остального

Если `fridaybot.ru` недоступен (регистратор заблокировал, зона пропала, оплата не прошла),
сервер поднимать бессмысленно: открывать и проверять будет нечего.

Порядок:
1. Зайти к регистратору (сейчас это Beget) и понять статус домена.
2. Если домен не спасти — взять **запасной**, который куплен заранее у **другого**
   регистратора, и направить его на новый сервер.
3. DNS запасного домена лучше держать у третьей стороны (Cloudflare, Яндекс DNS),
   чтобы перепривязка IP не зависела от регистратора.
4. Дальше все шаги делать с новым доменом:
   `DOMAIN=новый.домен recovery/restore.sh --apply --yes ...`
   Скрипт сам заменит `server_name` в конфигах nginx.

Что придётся поменять руками: redirect URI в Яндекс OAuth, вебхук Telegram,
ссылки в письмах и S3. Полный список — в `ARMAGEDDON.md`, сценарий F.

## Шаг 1. Новый сервер (10–20 минут)

Любой VPS: Debian 13, 4 ядра, 8 ГБ памяти, 60 ГБ диска. Хостер неважен.

Получил IP и пароль root — сразу переключи вход на ключ.

## Шаг 2. Установка одной строкой (2 минуты)

```
curl -fsSL https://raw.githubusercontent.com/Archakovss/pixel/main/install.sh | bash
```

Что увидишь:

```

   ✓ curl
   ✓ git
   ✓ python3

[2/4] Кладу файлы
```

Если чего-то не хватает — установщик скажет, чего именно, и **остановится**,
ничего не сломав. Тогда: `apt install nodejs npm git python3` и повторить.

## Шаг 3. Ключ модели (1 минута)

```
echo 'КЛЮЧ' > ~/.pixel/provider.key
chmod 600 ~/.pixel/provider.key
```

Проверка:

```
pixel doctor
```

Что увидишь: список из одиннадцати пунктов — node, curl, git, шлюз, ключ,
postgres, pm2, nginx, tmux, диск, каталог данных. Красные — доустановить:
`apt install postgresql nginx`.

## Шаг 4. Подъём (5–10 минут для базы, ~30 секунд сам скрипт)

```
pixel recover
```

или, если снимок лежит файлом:

```
recovery/restore.sh --apply --yes \
  --from s3://БАКЕТ/dr/ДАТА --passphrase-file ~/.pixel/dr.pass
```

Что увидишь:

```
[1/6] Проверяю машину        ✓ 0 с
[2/6] Беру снимок            ✓ 1 с
[3/6] Восстанавливаю базу    ✓ 6 с
[4/6] Поднимаю код           ✓ 25 с
[5/6] Настраиваю сайт        ✓ 0 с
[6/6] Приёмка                ✓ 0 с
──────────── и т о г ────────────
всего: 32 с
✔ Готово. Ядро поднято.
```

Если шаг красный — скрипт останавливается и говорит, на чём. Не «попробовать ещё
раз», а прочитать причину.

Можно и словами: `pixel` → «Восстанови Ядро по карточке Армагеддона, снимок самый
свежий, спрашивай, если нужно решение».

## Шаг 5. Проверка (5 минут)

- `https://fridaybot.ru/core/health` → `ok: true`, `loaded_commit` = `head`.
- Панель открывается, чат отвечает.
- Один клиентский сайт открывается.
- Telegram-бот отвечает.

Не совпало — сказать Пикселю, какой пункт не сошёлся. Не «подождать».

---

## Чего НЕ делать

- Не восстанавливать поверх работающего сервера. Скрипт сам откажется.
- Не менять DNS до зелёного `/health`.
- Не гнать `rm -rf` и `DROP` из паники: снимок цел, база разворачивается заново.
- Не верить зелёной галочке без открытия сайта: проверяется потребителем.
